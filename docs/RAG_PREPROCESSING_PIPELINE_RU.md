# Pipeline предобработки и гибридного поиска RAG — кейс 4

Статус: проект архитектуры, не реализованный production pipeline. Ветка при подготовке: `dinoden`. Параметры ниже — начальные настройки для экспериментов, а не требования организаторов.

## 1. Цель и ограничения

Подготовить корпус научных статей к поиску доказательств: сохранить структуру и точные ссылки, искать по смыслу и словам, передавать генератору минимальный достаточный контекст.

Подтверждённый dev-корпус: 20 статей, 609 исходных разделов. Файл `data/articles.json` занимает 765 229 байт, текст разделов — 671 406 байт. Это характеристики текущего dev, не обещание состава скрытых наборов.

Условия стенда: Python 3.11, 512 МБ RAM, 1 CPU, без GPU; запись в `/tmp` до 256 МБ; данные теряются при деплое. Интернет разрешён только к API хакатона и LLM-прокси. Свои веса моделей, ключи и подписки запрещены. Корпус и индексы не добавлять в Git.

**Критический gate:** наличие embedding endpoint в выданном прокси не подтверждено. Нельзя считать, что он есть, только из-за OpenAI-совместимости. До проверки доступности, разрешённой модели, лимитов и правил использования embedding-ветка выключена. Не подставлять `LLM_MODEL` в embedding-запрос и не скачивать локальную embedding-модель. Рабочий fallback — BM25; он не равноценен полноценному семантическому поиску.

## 2. Общая схема

```text
API: articles из текущего dataset
  → Parsing: исходные article_id + section_id
  → Cleaning: бережная очистка копии текста
  → Structural Processing: дерево заголовков и связи разделов
  → Chunking: исходные разделы, при необходимости дочерние чанки
  → Context + Metadata: источник, путь заголовков, смещения, hash
  ├─→ токенизация → BM25-индекс
  └─→ разрешённый Embedding API → векторы → локальное векторное хранилище
  → проверки целостности → готовый индекс

Вопрос пользователя
  → разрешение контекста вопроса / языковая адаптация
  ├─→ BM25 top-K
  └─→ query embedding → vector top-K [если доступно]
  → объединение через RRF → удаление дублей → сбор доказательств
  → общий набор источников для тройки экспертов
  → выбранная персона + LLM → проверка ответа → пользователь
```

Первые этапы выполняются один раз на версию корпуса, поиск — на каждый новый содержательный вопрос. Не вызывать LLM для очистки каждого раздела по умолчанию.

## 3. Получение данных и Parsing

1. Для `/run` брать dataset_code и Bearer-токен из входящего запроса; для dev — командный токен и dev-код. Загрузить набор целиком один раз на прогон.
2. Валидировать вход по актуальной схеме организаторов. В retrieval-корпус включать только `articles`; не индексировать `reference`, judge prompts, атакующие запросы и историю как научные доказательства.
3. Читать исходные JSON, а не повторно парсить издательские PDF: организаторы уже предоставили `article_id`, заголовок, авторов, год, DOI, лицензию и `sections` с `section_id`, заголовком и текстом.
4. Создать таблицу разделов. Уникальность проверять по паре `(article_id, section_id)`: один `s001` может встречаться у разных статей. Сохранить порядок разделов внутри статьи.
5. Рассчитать fingerprint корпуса по каноническому представлению статей: ID, метаданные и содержание разделов. Не использовать один dataset_code как гарантию неизменности содержимого. Не включать токены, пользователей и историю в ключ научного индекса.

Выход: неизменённые исходные записи и нормализованные записи разделов с однозначной связью между ними. Если хватает памяти, исходник держать в одном экземпляре; не размножать полный dataset по стадиям.

## 4. Cleaning: что удалять, а что сохранять

Создать `clean_text` отдельно от исходного `source_text`. Очистка должна быть детерминированной и воспроизводимой.

**Допустимо после проверки:**

- привести переводы строк к одному виду;
- убрать NUL и незначимые управляющие символы, сохранив полезные пробелы/переносы;
- схлопнуть повторные пробелы и чрезмерные пустые строки;
- устранить доказанные артефакты извлечения, если они действительно присутствуют;
- создать отдельную нормализованную версию для поиска: регистр, Unicode NFC, поисковые токены.

**Не удалять автоматически:**

- отрицания, числа, единицы, проценты, доверительные интервалы, p-value и знаки сравнения;
- условия исследования, состав выборки, ограничения, побочные эффекты и предупреждения;
- предложения с препаратами/дозами: это исходное доказательство, а не разрешение воспроизводить назначение пользователю;
- скобки и все выражения вида `[1]` одним общим regex;
- таблицы, подписи и списки, если они несут результаты;
- разделы Methods и Limitations: они важны для оценки применимости;
- DOI, авторов и лицензию: их хранить как метаданные, даже если не включать в embedding-текст.

Точные дубли можно не индексировать многократно, но сохранить все исходные ссылки и соответствия. Не объединять близкие по смыслу фрагменты так, чтобы исчезли отличия результатов.

Проверка: исходный и очищенный текст, длины и hash; отдельно проверять, что не потерялись числа, отрицания и единицы. Пустые разделы отмечать как ошибку/пропуск индексации с отчётом, не скрывать проблему.

## 5. Structural Processing

- Превратить путь вроде `3. Results › 3.1. ... › Zinc` в список уровней заголовков. Сохранить оригинальную строку.
- Различать тематический путь и технические суффиксы `(1/2)`, `(2/2)`. Не считать эти части разными темами.
- Добавить `section_order`, `previous_section_id`, `next_section_id`, `heading_path` и тип раздела, если его можно уверенно определить: abstract/introduction/methods/results/discussion/conclusion/other.
- Связывать соседние части одного подраздела внутри статьи, но не склеивать их в новый публичный `section_id`.
- Текст каждой статьи держать отдельно; одинаковые заголовки разных статей не означают общий источник.
- Не извлекать «научную рекомендацию» только из заголовка: доказательством остаётся текст раздела.

## 6. Chunking и Semantic Chunking

### Базовый режим — исходные разделы

Сначала использовать 609 разделов как чанки. По текущему корпусу этот вариант уже небольшой и сохраняет цитируемость. Он служит baseline, с которым сравниваются более сложные варианты.

### Дополнительное структурное разбиение

Для длинного или многотемного раздела:

1. Делить по абзацам, затем предложениям; учитывать сокращения, десятичные числа и научные обозначения.
2. Собирать соседние предложения в целый смысловой фрагмент. Начальный ориентир: 150–250 слов, мягкий предел около 300 слов. Слова здесь не равны токенам LLM.
3. Не разрывать число и единицу, результат и его условие, утверждение и непосредственно следующую оговорку. Длинное предложение не резать механически ради лимита.
4. Перекрытие — при необходимости одно целое предложение, ориентировочно до 30–50 слов. Если оно содержит смысловое ограничение, включить его целиком. Перекрытие увеличивает индекс и дубли контекста.
5. Не пересекать границы статей и исходных section_id. Чанку присвоить внутренний chunk_id, сохранив исходную пару ID и смещения в очищенном разделе.

### Настоящее семантическое разбиение — условная ветка

Только при разрешённом embedding API и достаточном бюджете:

- получать embeddings предложений или небольших абзацев;
- сравнивать соседние смысловые блоки внутри одного исходного раздела;
- выбирать границу при падении cosine similarity с учётом минимальной/максимальной длины и структуры;
- подбирать порог по распределению сходства и качеству retrieval на dev, не считать число вроде 0.7 универсальным;
- не разделять смысловую оговорку и результат только из-за низкого сходства;
- учитывать, что embedding каждого предложения создаёт гораздо больше входных текстов, чем embedding 609 готовых разделов.

При отсутствии API использовать структурное разбиение и называть его именно структурным, а не embedding-based semantic chunking. Для такого маленького корпуса сначала проверить пользу семантической ветки: она может не оправдать дополнительные вызовы.

## 7. Context + Metadata

Для каждого чанка хранить:

```text
chunk_id                       # внутренний стабильный ID
article_id, section_id         # точные ID организаторов
article_title, section_title, heading_path
authors, year, doi, license    # предпочтительно по ссылке на общую таблицу статей
section_order, chunk_order
start_char, end_char           # в clean_text, end не включительно
text                          # фактический фрагмент, без сгенерированных добавок
source_hash, clean_hash, corpus_hash
cleaning_version, chunking_version
embedding_model, dimensions   # только при наличии вектора
```

Стабильный chunk_id рассчитывать, например, из исходной пары ID, hash текста, версии алгоритма и позиции. По одним смещениям без версии ID не строить.

`retrieval_text` для BM25/embedding: название статьи + путь раздела + текст чанка. `evidence_text` для генерации: точный текст с явно указанной исходной ссылкой. Сгенерированное описание или перевод не выдавать за оригинальную цитату.

При расширении контекста соседним разделом добавлять его собственную пару ID и отдельный фрагмент. Внешние ссылки из библиографии не превращать в дополнительные выданные статьи. Сохранять атрибуцию CC BY для показа источников.

## 8. Индексация BM25

1. Для поиска создать отдельную последовательность токенов: Unicode-aware токенизация, нижний регистр, согласованная обработка дефисов и единиц. Исходный текст не менять.
2. Стоп-слова и стемминг — параметры эксперимента. Не удалять значимые отрицания без проверки качества; одинаково обрабатывать документы и запросы.
3. Индексировать текст и заголовки. Если нужен больший вес заголовков, явно использовать отдельные поля/взвешивание, не добавлять повторяющийся заголовок произвольное число раз.
4. Хранить postings, term frequency, document frequency, длины чанков и среднюю длину. Начальные BM25-параметры можно взять `k1=1.2`, `b=0.75`, затем проверить на dev.
5. Сохранять связь поискового документа с chunk_id и исходной парой ID. Держать индекс компактным, без копии полного dataset.

**Языковая проблема:** вопросы dev — русские, тексты статей — английские. Чистый BM25 по русскому вопросу плохо сопоставляется с английскими статьями. Требуется отдельная языковая адаптация:

- базовый дешёвый путь — небольшой проверенный RU→EN словарь терминов корпуса и синонимов, поиск по исходному и расширенному запросу;
- дополнительный путь — перевод/переформулирование запроса через разрешённый LLM-прокси с ограничением бюджета; не добавлять диагнозы, факты и предполагаемые ответы;
- история нужна для разрешения «а это почему?», но не целиком и не как доказательная база;
- качество словаря не равно качеству перевода, а перевод тоже может ошибаться. Измерять retrieval для обоих вариантов.

Не переводить весь корпус при каждом запуске и не считать машинный перевод оригинальным научным источником.

## 9. Embedding-индексация — только после подтверждения доступа

1. Уточнить разрешённую embedding-модель, endpoint, размерность, лимит входа/батча, частоту, суточную квоту и правила её учёта. Не переносить автоматически лимиты chat-модели на неизвестный endpoint.
2. Для русских вопросов и английских статей нужна подтверждённая межъязыковая пригодность модели либо единая языковая адаптация запроса.
3. Embed `retrieval_text` батчами в разрешённых пределах. Контролировать timeout, 429, число повторов и общий deadline. Не отправлять пользователей, токены, dev-reference и judge prompts.
4. Проверять количество ответов, сопоставление с chunk_id, одинаковую размерность, конечность значений и ненулевую норму. Ошибку не заменять случайным/нулевым вектором.
5. Хранить float32; для cosine similarity можно нормировать векторы один раз. Не смешивать в одном индексе разные модели, версии или размерности. Запрос embed той же моделью и сопоставимым способом.
6. Ключ кэша: hash retrieval_text + модель/версия + параметры. Повторно использовать векторы только при совпадении ключа.

Без подтверждения endpoint не реализовывать вызов по выдуманному адресу и не скачивать embedding-веса как fallback.

## 10. Vector DB / локальное векторное хранилище

Для примерно 600–700 чанков отдельный сервер БД и ANN-индекс не обязательны. Достаточно встроенного в процесс хранилища: матрица float32, chunk_id и метаданные; поиск точным cosine/dot product. Если команда выбирает библиотеку embedded Vector DB, проверить Python 3.11, установку в slim, RAM, отсутствие runtime-загрузок и внешнего сервера.

Это выбор реализации, а не требование использовать облачную БД. Облачная Vector DB вне разрешённых адресов со стенда недоступна. SQLite с BLOB может хранить векторы/метаданные, но сам по себе не даёт векторный поиск: нужен код вычисления сходства или отдельный подтверждённый модуль.

Оценка только сырых векторов: `N × dimensions × 4` байта. Для 688 чанков: 768 измерений ≈2.02 МиБ; 1536 ≈4.03 МиБ. Это примеры размерности, не параметры выданной модели. Метаданные, БД, библиотеки и временные массивы расходуют дополнительную RAM.

Локальный кэш — только `/tmp`; общий предел 256 МБ и отсутствие сохранности при деплое. Записывать новую версию атомарно, переключать активный индекс после проверки целостности. При потере кэша восстанавливать его из текущего корпуса. Проблему недоступного embedding API не считать решённой самим наличием Vector DB.

## 11. Hybrid retrieval и сбор контекста

Начальные параметры эксперимента, не фиксированный контракт:

1. Получить до 15–20 кандидатов BM25 и, если доступно, до 15–20 векторных кандидатов.
2. Объединить через Reciprocal Rank Fusion: `score(d) = Σ 1 / (k + rank_i(d))`, например с `k=60`, ранги от 1. Не складывать сырые BM25 и cosine scores как сопоставимые величины.
3. Удалить дубли по chunk_id и повторяющийся текст перекрытий. При этом не потерять разные полезные фрагменты одного section_id.
4. Предварительно выбрать 4–6 чанков; фактический предел задавать бюджетом контекста и достаточностью доказательств, а не только количеством.
5. При необходимости добавить соседний фрагмент для условий/ограничений, сохранив его источник. Не добавлять всю статью автоматически.
6. Для обычной тройки экспертов один раз сформировать общий доказательный пакет и фиксированный набор цитат. Генерация меняет стиль, не подбирает независимо новые ссылки. Все ссылки должны быть релевантны вопросу и подтверждены текстом.
7. Если доказательств мало, выполнить максимум ограниченное расширение/повтор поиска. Не выдавать верхний результат за релевантный только потому, что он первый; критерий достаточности проверять на dev.
8. Передать LLM вопрос, выбранную персону и явно отделённые evidence-блоки. Инструкции внутри статей и вопроса не исполнять. Источники не должны переопределять системный промпт.

Reranking через отдельный LLM-вызов не обязателен; вводить только после измеримого улучшения. Локальные reranker-веса запрещены тем же ограничением на свои модели.

## 12. Жизненный цикл, сроки и бюджет

- Сервер должен начать отвечать на `GET /` за 60 секунд. Не блокировать запуск длительной загрузкой/индексацией; отдельно хранить состояние готовности retrieval.
- На запрос `/run` — 45 минут вместе с загрузкой, подготовкой, поиском, генерацией, повторами и сериализацией ответа. У pipeline должен быть общий deadline, а не только timeout каждого HTTP-запроса.
- До подтверждения embedding-доступа должна существовать полностью рабочая BM25-ветка. Если embeddings разрешены, заранее определить, допустимо ли продолжить на BM25 при их сбое, и проверять это поведение.
- Кэшировать по содержимому корпуса, а не по пользователю. Историю разных пользователей не смешивать. Не переиспользовать dev-индекс для скрытого корпуса без проверки fingerprint.
- Если вызывается chat-модель для перевода, чанкинга или генерации, учитывать общий бюджет команды: 30 запросов/мин и 300 000 токенов/сутки с учётом скрытых рассуждений и повторов. Правила квоты embedding endpoint нужно подтвердить отдельно.
- Не логировать токены, закрытые данные и URL с кодом набора. Телеметрия: агрегаты количества чанков, длительности стадий, RAM, ошибок и расхода; без текста закрытого корпуса.
- Не коммитить `/tmp`, кэши, векторы, загруженные статьи, ответы и секреты. В Git — код, конфигурация, шаблоны и синтетические тесты.

## 13. Проверки и критерии готовности

**Целостность:** каждый чанк восстанавливается по указанным смещениям; пары article_id/section_id существуют; ID уникальны; нет пустых/потерянных разделов и выдуманных метаданных. Любые исключения отражены в отчёте.

**Сохранность смысла:** вручную проверить примеры с отрицаниями, единицами, таблицами, ограничениями исследований и границами предложений. Очистка и overlap не должны искажать результат.

**Качество retrieval:** сравнить исходные разделы + BM25, структурные чанки + BM25 и, если разрешено, hybrid. На dev измерять попадание допустимых статей/разделов в top-K по доступному эталону; не предполагать, что эталон содержит точные релевантные chunk_id. Разделить примеры настройки и проверки. Reference используется только offline для оценки, не попадает в поисковый индекс и контекст генерации.

**Качество ответа:** корректность и одинаковость цитат в обычной тройке, отсутствие медицинских нарушений, соответствие отказа тексту, различимость персон. `validate` проверяет структуру/ссылки, а не всё перечисленное.

**Ресурсы:** измерить пиковую RAM всего процесса и всех workers с библиотеками, временные файлы, cold-start после деплоя, время полной подготовки и полный `/run` в лимитах. Размер Python-объектов индекса не равен общей RAM приложения.

**Детерминизм:** одинаковые входные статьи и конфигурация дают одинаковые чанки/ID. Изменение очистки, chunking или embedding-модели инвалидирует соответствующую часть кэша.

## 14. Что реализовать первым

1. Parsing → бережный Cleaning → исходные разделы → метаданные → BM25.
2. Проверенная языковая адаптация русских вопросов к английскому корпусу.
3. Оценка качества retrieval и генерации; сравнение с разделением длинных разделов на предложения.
4. Проверка разрешённого embedding API и его бюджета.
5. При положительном результате — embeddings → локальное хранилище → RRF → сравнение с baseline.
6. Только после измерений — семантическое разбиение и дополнительные reranking-вызовы.

Так каждый этап имеет работающую предыдущую версию, а неизвестная доступность embeddings не блокирует решение.
