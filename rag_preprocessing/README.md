# Предобработка и поиск RAG

Работает на Python 3.11 без сторонних пакетов, GPU, скачивания моделей и внешней БД. По умолчанию сетевых вызовов нет. Подробная архитектура: `docs/RAG_PREPROCESSING_PIPELINE_RU.md`.

## Что реализовано

- Вход: список статей, dataset, API-ответ с `dataset` или путь к JSON. В индекс попадают только статьи; reference, пользователи, история и judge prompts исключаются.
- Валидация используемых полей и уникальности ID. Это не замена валидации полного dataset по JSON Schema организаторов.
- Неразрушающая очистка текста, исходник и cleaned-версия, пути заголовков, связи соседних разделов, метаданные авторов/DOI/лицензии.
- Режимы `sections` (исходные разделы), `structural` (целые предложения, мягкий предел размера, перекрытие) и `semantic` (границы по сходству embeddings).
- Стабильные chunk_id, исходные article_id/section_id, смещения в cleaned-тексте, hash корпуса и версии конфигурации.
- BM25 в SQLite, небольшой RU→EN словарь расширения запросов.
- Опциональные embeddings, хранение float32-векторов в SQLite и точный cosine search. Vector search выполняет Python-код; сама SQLite не становится ANN-движком.
- Hybrid retrieval через RRF; сбор контекста с объединением перекрывающихся фрагментов одного раздела.
- Атомарная пересборка: при ошибке старый индекс остаётся. Повторная сборка неизменённого корпуса с теми же настройками использует готовый индекс без embedding-вызовов.

## CLI

Выполнять из корня репозитория. `python` должен указывать на установленный Python 3.11 или новее.

```powershell
# Исходные разделы: baseline, 609 чанков на текущем dev
python -m rag_preprocessing build --input data/articles.json --output tmp/rag/index.sqlite3

# Дополнительное структурное разбиение: 688 чанков на текущем dev
python -m rag_preprocessing build --input data/articles.json --output tmp/rag/structural.sqlite3 --mode structural --max-words 250 --overlap-words 40

# Только локальная разработка: эта команда явно печатает найденные фрагменты
python -m rag_preprocessing search --index tmp/rag/index.sqlite3 --query "Как кофеин влияет на сон?" --top-k 5

python -m unittest discover -s tests -v
```

Вместо `data/articles.json` можно передать `data/dataset.json` или полный API-ответ. Локальные пути не зашиты в runtime. Если `--output` не задан, используется системная временная папка `sain-rag/index.sqlite3`; на Linux это обычно `/tmp/sain-rag/index.sqlite3`.

`--timeout` у build по умолчанию 120 секунд, у search — 30. Для полного backend-прогона передавайте общий абсолютный `deadline` через Python API; не обнуляйте 45-минутный бюджет при каждом этапе. CPU-операция или сетевое чтение могут завершиться до следующей проверки deadline, поэтому backend также отвечает за внешний HTTP-timeout.

## Вызов из backend

```python
import time
from rag_preprocessing import Config, build_index, pack_context, search

# dataset — текущий набор, полученный backend через API с правильным токеном.
# Первая индексация — после запуска HTTP-сервера, не блокируя старт на 60 секунд.
deadline = time.monotonic() + 45 * 60
index_path = "/tmp/sain-rag/index.sqlite3"
report = build_index(dataset, index_path, Config(), deadline=deadline)

hits = search(index_path, question, top_k=5, deadline=deadline)
evidence = pack_context(index_path, hits, max_chars=12000)
citations = list(dict.fromkeys(
    (block["article_id"], block["section_id"]) for block in evidence
))
# Передать evidence и citations генератору. Для обычной тройки экспертов
# использовать общий доказательный пакет, меняя только промпт персоны.
```

Пустой список evidence — недостаток доказательств, а не разрешение отвечать из памяти модели. Фиксированный top-K и RRF-score не доказывают релевантность. Порог достаточности нужно подобрать на dev и проверять совместно с генерацией.

`max_chars` — бюджет символов, не токенов; реальные расходы проверять по модели. `pack_context` не обрезает фрагмент посередине предложения: не поместившийся блок пропускается. Не делайте max_chars настолько маленьким, чтобы потерять все доказательства.

## Как включить embeddings

**Не включать до подтверждения организаторами endpoint, модели, квот и допустимости использования.** Локальных весов и автоматического переключения на чужой сервис нет.

Нужно настроить локальные переменные окружения, не помещая значения ключей в Git:

- `RAG_EMBEDDINGS_APPROVED=1` — явное включение после проверки условий;
- `RAG_EMBEDDING_URL` — полный подтверждённый HTTPS endpoint, без query-параметров; адрес автоматически не угадывается;
- `RAG_EMBEDDING_MODEL` — подтверждённое имя embedding-модели, не chat-модель из `LLM_MODEL`;
- `LLM_BASE_URL` и `LLM_API_KEY` — уже выданные настройки прокси.

Адаптер принимает только тот же origin и префикс пути, что у `LLM_BASE_URL`, не следует редиректам, не печатает URL/ключи/тексты ошибок API. Формат запроса — OpenAI-style `model` + `input`, ответ — `data[].index` и `data[].embedding`. Другой контракт требует адаптации после сверки с документацией.

```powershell
# После подтверждения и настройки env:
python -m rag_preprocessing build --input data/articles.json --output tmp/rag/hybrid.sqlite3 --embeddings --timeout 300
python -m rag_preprocessing search --index tmp/rag/hybrid.sqlite3 --query "Как кофеин влияет на сон?" --embeddings

# Дополнительные embedding-вызовы для предложения/абзаца каждого раздела:
python -m rag_preprocessing build --input data/articles.json --output tmp/rag/semantic.sqlite3 --mode semantic --embeddings --timeout 1800
```

Через Python API: `provider = ProxyEmbeddings.from_env()`, затем `build_index(..., provider=provider)` и `search(..., provider=provider)`. Поиск без provider работает как BM25 даже по индексу с векторами. При ошибке явно включённой embedding-ветки операция завершается ошибкой; скрытого деградирования и бесконечных повторов нет. Backend может явно выбрать отдельный BM25-индекс как fallback.

Запросы одного адаптера разнесены минимум на 2.1 секунды; это локальная предосторожность, не подтверждённый лимит embeddings и не общий limiter команды. Таймаут HTTP — 30 секунд, батч — 16 текстов по умолчанию. Backend должен координировать общую частоту/токены, квоты, предельный размер input и deadline. Повторов автоматически нет. Семантическое разбиение вызывает embeddings для предложений и затем для чанков; это может стоить намного дороже простого индексирования разделов.

## Ограничения реализации

- RU→EN словарь маленький; это не полноценный перевод или русская лемматизация. Не гарантирует поиск произвольного русского вопроса. Расширять только после проверки качества; разрешённый LLM-перевод можно подключить отдельно с учётом квоты.
- Границы предложений определяются эвристикой с несколькими научными сокращениями. Сложные формулы/сокращения могут потребовать улучшений. Длинное предложение не разрезается механически; превышение мягкого лимита отражается в `warnings`.
- Semantic threshold и размеры чанков — настройки эксперимента. Семантические границы не гарантируют сохранение всех смысловых зависимостей; нужна ручная проверка.
- Хранилище предназначено для небольшого корпуса. Векторный поиск точный и линейный; сервер Vector DB и ANN не используются. Между разными пересборками embedding-векторы по отдельным текстам не переиспользуются: кэшируется целый готовый индекс. Любое изменение конфигурации приводит к полной пересборке.
- Атомарное переключение защищает от неполного файла, но backend должен сериализовать конкурирующие build одного пути и синхронизировать смену индекса с активными читателями. В Windows открытый чужим процессом файл может мешать замене; приложение получит ошибку, старый индекс останется.
- Не реализованы HTTP-сервер, генерация ответов, проверка медицинских формулировок и полный `/run`: модуль подключается к backend как отдельный этап.

## Ресурсы и безопасность

На текущем корпусе SQLite baseline занимает около 14.74 МиБ, structural — 15.37 МиБ. Здесь сохраняются исходники, cleaned-тексты, чанки, метаданные и SQLite-индексы; это больше прежней оценки сериализованного JSON. Оба файла вместе помещаются в `/tmp` 256 МБ, но в production обычно нужен один активный индекс. Во время атомарной пересборки одновременно существуют старый и новый файлы.

Это размер диска, не RAM. Проверить память всего backend со всеми workers и выбранными зависимостями в контейнере 512 МБ. Хранить только нужные наборы и кэши; после деплоя всё восстанавливается.

CLI build выводит агрегаты, а не содержание корпуса. CLI search выводит тексты только по явной команде: не направлять этот вывод в production-логи и не использовать на закрытом наборе в публичных отчётах. `.gitignore` защищает новые `tmp/`, `.rag-cache/`, SQLite-файлы, Python-кэши и `.env`; уже отслеживаемые файлы игнорирование из Git не удаляет.

Тесты используют только синтетические статьи и локальные тестовые векторы. Внешние API не вызываются, токены команды не расходуются.
