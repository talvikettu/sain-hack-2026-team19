# RAG-агент: пробный прогон первых 10 запросов

Агент связывает подготовленный индекс с LLM-прокси. Работает без сторонних Python-зависимостей. Не является HTTP-backend и не реализует endpoint `/run`.

## Схема

1. Принять вопрос, `expert_id`, ID пользователя и записи, timestamp.
2. Проверить экспертный ID по разрешённому списку: `clinician`, `biohacker`, `nutritionist`. Frontend позже передаст этот ID в backend; backend обязан проверить право доступа пользователя к диалогу.
3. По умолчанию используется экономный профиль `compact`: историю передавать только при явной отсылке к прошлому, до 4 сообщений и 2000 символов, только этого пользователя и до timestamp запроса. Это эвристика: неявная отсылка может быть пропущена. История передаётся как недоверенные данные. Профиль пользователя и дата рождения в запрос не входят. Старый `full` сохраняет до 6 сообщений/3500 символов на каждом запросе.
4. Для явных отсылок к прошлому добавить последние пользовательские сообщения в поисковый запрос. Это эвристика, не полноценный rewrite через LLM.
5. Выполнить BM25 с RU→EN расширением. В `compact` явный фактор вопроса получает приоритет над второстепенными словами; из 20 кандидатов выбираются до 3 с умеренным приоритетом результатов/выводов над введением/методами, до 4500 символов контекста. Это ручные общие эвристики, не обученный классификатор. `full` оставляет старые 5 фрагментов/12 000 символов. Embeddings в этом демонстрационном агенте не включены.
6. В `compact` собрать `prompts/system_compact.md` и одно исходное описание роли/стиля эксперта из dataset, без дублирующих длинных промптов. Модель возвращает только `text`, `refused`, `refs` с короткими номерами evidence. Код преобразует номера в исходные ID и добавляет record_id. В `full` сохранена прежняя сборка длинных инструкций и полного выходного JSON. Научные фрагменты, история и вопрос — JSON-блок данных.
7. Вызвать chat completions через `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` из env. Не скачивать веса и не использовать свои ключи/подписки.
8. Проверить `finish_reason`, JSON, обязательные поля, boolean отказа, непустые цитаты, их уникальность и принадлежность переданным доказательствам, совпадение inline-ссылок со списком.
9. При ошибке структуры — не более одной попытки пересоздать ответ. Ошибка сети/429 не вызывает автоматические повторы. Общий предел демо — число вопросов + 2 вызова, а не 2 вызова на каждый вопрос.
10. В групповом прогоне выбрать один общий раздел до генерации по `group_id`. Список источников проверяется для каждого ответа. При сравнении экрана с бумажной книгой поиск учитывает оба варианта и, если сказано в вопросе, дневное освещение. Общие тематические запросы и исходный текст тоже участвуют в поиске. Видимый текст очищается перед проверкой ссылок.

Для локальной проверки поиска без модели запустите `python scripts/evaluate_retrieval.py` из корня проекта. Отчёт в `tmp/retrieval_evaluation/` показывает отдельно кандидатов и источник, выбранный для промпта. Dev-эталон используется только для сравнения после поиска.

Готовый ответ содержит `record_id`, `text`, `refused`, `citations` и может быть обёрнут backend в `{"requests": [...]}`. Остальная диагностическая информация не должна попадать в эту схему.

## Локальный предпросмотр — без сети и ключей

Из корня репозитория:

```powershell
python -m rag_agent --limit 10 --dry-run --output tmp/rag_demo_preview

# Подготовить все 60 без единого LLM-вызова:
python -m rag_agent --limit 60 --dry-run --profile compact --output tmp/rag_preview_60
```

`preview.json` содержит точные сообщения, которые агент подготовил для модели: инструкции, выбранную персону, историю, вопрос и retrieved evidence. Секретов и Authorization там нет. Файл содержит данные dev и предназначен для локального просмотра, а не публикации.

Чтобы исключить историю из предпросмотра и последующего запуска, добавить `--no-history`.

## Реальный прогон — расходует квоту команды

Предварительно настроить `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в окружении. На стенде они уже заданы. Для локального запуска ключ загрузить из `team19/llm.key` без печати значения; файл и env не публиковать.

```powershell
python -m rag_agent --limit 10 --output tmp/rag_demo_first10
```

Настройки по умолчанию: до 120 секунд на HTTP-вызов, 1800 выходных токенов с учётом reasoning (`full`: 2500), интервал между стартами запросов минимум 2.1 секунды, deadline всего демо 1200 секунд. Уменьшение max_tokens — ограничение максимума, не гарантированная экономия фактических токенов; слишком маленький максимум обрезает ответ.

CLI поддерживает 1–60 вопросов. Локальный token budget — 120 000, меняется через `--token-budget`; он может остановить полный прогон раньше 60 вопросов. Перед вызовом используется консервативная оценка по UTF-8 байтам, после него — реальный `usage.total_tokens`. Это не общий счётчик суточной квоты команды; расходы остальных участников неизвестны. Полный live-прогон запускайте только после проверки бюджета, результатов малого теста и оценки лимита на день.

Результаты записываются после каждого вопроса:

- `report.md` — читаемые вопросы, ответы, цитаты, отказ, время и токены;
- `run.json` — ответы и диагностика, включая finish_reason и usage;
- `answers.json` — только успешные ответы в оболочке `requests`;
- `index.sqlite3` — локальный индекс корпуса.

Если в папке уже есть `run.json`, CLI отказывается повторять вызовы: нужно явно выбрать новую папку. При первой ошибке прогон останавливается, сохраняя частичные результаты и не расходуя бюджет на следующие вопросы вслепую. Индекс и отчёты по умолчанию в игнорируемом `tmp/`.

## Python API для будущего backend

```python
from rag_agent import ChatClient, RAGAgent

client = ChatClient.from_env()
agent = RAGAgent(index_path, dataset["experts"], client,
                 history=dataset["chat_history"])

result = agent.answer(question, expert_id,
                      user_id=authenticated_user_id,
                      record_id=request_id,
                      at=request_timestamp,
                      deadline=shared_run_deadline)
answer = result["answer"]
```

Один объект агента рассчитан на последовательный демонстрационный прогон. Для конкурентного backend нужны ограниченный кэш, координация общих лимитов, изоляция истории/диалогов и синхронизация фиксации цитат. После успешного ответа демо не дописывает его в исходную историю: примеры являются независимыми записями набора, а не новым последовательным разговором. В интерактивном приложении сохранение проверенного ответа делает backend.

## Что проверки не гарантируют

В `compact` после проверки формата агент отклоняет внешние ссылки, HTML, явное обращение к проверяющему и дословное воспроизведение длинного абзаца системного промпта. Допускается одна повторная генерация с инструкцией сервера, без передачи отклонённого текста. Это проверки отдельных шаблонов, а не оценка всех способов обойти промпт.

Допустимый ID не доказывает опору тезиса на источник. Медицинский checker организаторов не вызывается, поэтому `medical_check` равен `not_performed`. Медицинские эвристики остаются флагами для ручной проверки. Локальные тесты с заглушкой проверяют обработку ответов кодом, а не устойчивость реальной модели.

`refused` проверяется на тип, но его смысловое соответствие тексту автоматически не доказано. Первые 10 вопросов — smoke test, не оценка качества на всём dev. Reference, judge prompts и эталонные ответы модель не получает.

При отсутствии evidence агент завершает операцию ошибкой до LLM-вызова: это не готовый UX для недостатка данных. Нужен отдельный продуктовый сценарий уточнения/повторного поиска.

`compact` — профиль по умолчанию. Короткие `refs` существуют только внутри LLM-запроса; внешний ответ остаётся `record_id/text/refused/citations`. Список refs и inline [N] проверяются, затем код подставляет настоящие article_id/section_id, без дополнительного вызова. Это снижает накладные расходы и риск ошибок формата ID, но не доказывает релевантность выбранного фрагмента.

`--profile full` позволяет воспроизвести старую сборку. В `prompts/system.md` остаётся прежний внутренний формат `sources`; только full-профиль использует доверенную инструкцию перехода к `citations`. Исходные длинные промпты сохранены как материалы для сравнения.
